# Rupert changelog

## Unreleased

- **`@rupert` in Buzz files bugs, requests and questions.** A teammate's plain-English message is classified (question / bug / request / direction), answered from the read-only reports, or filed as a report plus a task in **Rupert Feedback**, with the link posted back in the channel (`scripts/feedback_intake.rb`, JSON on standard input; prompt in `web/config/buzz_agent/acp.md`, rendered to `docs/ops/buzz-agent-prompt.txt`). Only senders on the allow-list (**Settings → Environment → `FEEDBACK_READY_SENDERS`**) can mark work ready for development; for everyone else it stays for review, whatever the message says. One report per message, rate limits, and every action in the Activity log tied to its message. `submit_feedback` gains `open_task`, `source`, `source_ref`, `source_sender` and `ready_for_development` with the same rules, and the owner can mark or clear ready when triaging at `/ai_feedback` (new Source filter). See `docs/ops/feedback-reports.md`.

- **Read-only MCP tools for operations and reports.** Connected assistants can ask `instance_status`, `recent_errors`, `sync_health`, `backup_freshness`, `deploy_status` (reads the auto-deployer's `status.json` when present), `list_feedback` and `report_context` (a report's attachments: browser details, JavaScript errors, server log lines, SQL queries, page snapshot). The operations tools use the existing `system:read` scope; the report tools use a new `feedback:read` scope (owner needs `settings.read` and must be a store administrator). Server-wide facts are limited to platform administrators and private workspaces; all text is scrubbed or marked untrusted. See `docs/mcp.md`.

- **The ladybug: report a bug, ask for something, ask a question.** A ladybug in the header opens a panel (Bug / Request / Question, what happened, how bad) that sends the report with the page address, build, browser details, recent JavaScript errors, a sanitized page snapshot and a screenshot (vendored `html2canvas-pro`, loaded only when used). It works on phones, in light and dark, with Escape and focus handling; password, card and token fields are hidden. Staff follow their reports' status under **My reports**; administrators see the attachments. See `docs/ops/feedback-reports.md`.

- **Report a bug, ask for something, ask a question (backend).** Any signed-in staff member can send a report to `POST /feedback_reports`; each one becomes an `AgentFeedback` row and a task in a new **Rupert Feedback** project assigned to the store owner, with a status page at **My reports**. Reports can carry admin-only attachments (screenshot, page snapshot, browser details, JavaScript errors, the session's recent server log lines and SQL queries with literals removed, all passed through the request-log parameter filter). New `feedback_attachments` table and `agent_feedbacks` columns (`source`, `task_id`, `ready_for_development`, ...). See `docs/ops/feedback-reports.md`.

- Fix the stock-comparison PDF test reader dropping a valid compressed byte and intermittently reporting empty PDF text; add a deterministic regression fixture. Production PDF generation is unchanged.

- **Buzz team chat card, and one prompt for the @rupert agent.** A **Buzz** speech-bubble icon in the header (staff with Overview access) opens `/buzz`: the agent's profile (name, public key, description), **Open chat** (deep link into the Buzz app for the configured relay and channel), **Get Buzz** (per-platform downloads for macOS, Windows, Linux, iPhone/iPad, Android and Web, each saying "Not available yet" when there is no link) and **Connect your own device** (relay and channel with copy buttons, plus a QR code for phones, drawn in the browser). It shows only public details and says "Buzz is not set up yet" until a relay is set. Link templates and download links are settings (`BUZZ_CHAT_LINK_TEMPLATE`, `BUZZ_CONNECT_LINK_TEMPLATE`, `BUZZ_DOWNLOAD_*`, `BUZZ_WEB_URL`; `buzz:` and `https:` only). Settings gains a Buzz status row with an on-demand **Check status** (relay reachable, agent registered). The agent's role, limits and tone now live in one place, `web/config/buzz_agent/`, used by the opencode chat agent and the `buzz-acp` prompt in `docs/ops/`. See `docs/ops/buzz.md`, including what could not be verified (mobile store links, a live relay).

- **One address: herbalhealers.rupertpos.com.** The retired hostnames (`rupert.stoverparc.org`, and the dead `rupert.cybersecuritypilot.org` / `herbalhealers.cybersecuritypilot.org`) now redirect to `HOST` with the same path when listed in the new `RUPERT_LEGACY_HOSTS` (301 for GET/HEAD, 308 for forms and API calls; `/up` health checks still answer on any host). `shopify.app.toml` points `application_url` and the OAuth redirect URLs at `herbalhealers.rupertpos.com` only — run `shopify app deploy` so the Partner Dashboard matches. - **Install updates from inside Rupert.** A new **System → Updates** page (instance operators only, `/system/updates`) shows the running build, what GitHub `main` has, what the server's updater (`rupert-autodeploy`) last did and the result of the last install. Operators can **Install update now** (or **Retry update** after a failed one), cancel a pending request, check GitHub on demand and choose **Automatically** or **Only when I click Install**. Rupert itself still never installs code: it leaves the request as a file in `storage/autodeploy/`, and the root-owned updater, which only reads that file's timestamp, still requires green CI, a fast-forward, a database backup and a healthy restart, and rolls back otherwise. The "Update available" banner now says whether the update will install automatically and sends operators to the page. A request made while already up to date does not approve a later commit, and a retry that fails is not repeated. On the host, reinstall `rupert-autodeploy.sh` and install the new `rupert-autodeploy.path` unit (see `deploy/ser8/README.md`); without the updater the page says updates are managed outside Rupert.

- **SQLite only.** PostgreSQL support is removed (issue #263): the `pg` gem and `libpq`/`postgresql-dev` build packages, the Postgres branch of `config/database.yml` (and `RUPERT_DB_ADAPTER`/`POSTGRES_*`), the `CI (postgresql)` job, the Postgres-only code in search, the System page and backups, the `db:postgres_to_sqlite`/`db:sqlite_to_postgres` tasks and `bin/migrate-to-sqlite`. `db/schema_sqlite.rb` is now the single `db/schema.rb`. `docker-compose.yml` keeps the database on the shared `rupert-storage` volume. SER8 auto-deploy now requires only `CI (sqlite3)`; reinstall `deploy/ser8/rupert-autodeploy.sh` on the host after merging. No data or database files are touched.

- **Product names page.** Stock gains a read-only **Product names** page (`/product_names`) that puts one name per product: the website (Shopify) name is primary, and Square (name as sold), SwipeSimple and C-Trax names are matched to it by SKU, then by normalized name, with fuzzy matches and SKUs shared by very different names flagged to verify. Three print sheets open as PDFs (name crosswalk, names to verify, unmatched items worksheet) and a CSV is available. The SwipeSimple Item Catalog has no sync yet; the page reads it from an optional private `storage/swipesimple_items.tsv` and leaves that column out when the file is absent. Nothing is written to any provider.

- **Time workspace you can navigate.** Timesheets, Punch report, Square history, C-Trax history, Team schedule and Payroll share one header with the current page marked. Timesheets opens on the review queue; the week calendar folds below it and opens itself when someone is clocked in. The **Punch report** (was Punch history) adds C-Trax shifts, one-tap pay-week/month/year ranges, a staff × source hours matrix and a red flag on any punch over 16 hours (a probable missed clock-out), also in the CSV. A **Time sources** strip shows records, counted hours, held records, date reach and last read per source. See `docs/ops/time-records-audit-2026-10-20.md` for the production counts and the records still to resolve.

- **Onboarding that gets out of the way.** New accounts see a one-question welcome on their home page (what will you mostly do here?) that lines up a learning path and offers a one-minute **guided tour** of the real page; skipping is one tap. A role-aware **Your first week** checklist then tracks real progress (saved connection, successful sync, finished lesson, second account, customised dashboard…) until it is done or hidden. Tours exist for the dashboard, sales, inventory, counts, alerts, Learn Rupert and the staff home, plus customers, sync, credentials, the register, timesheets, staff, receipts, tasks, accounts, close & review and reports; they never start by themselves and record completion per account.
- **Help everywhere.** A **?** button (and the `?` key) opens a help panel with this page's guide, its tour and lesson, and live search across lessons, definitions and tours. Labels gain a small **?** mark with a plain-language definition in place; **How is this calculated?** disclosures show the page's own numbers step by step (today's sales by source, cover and suggested reorder, estimated pay, count variance and more). Dozens of new definitions cover stock, money, access and team words.
- **Deeper training modules.** Seven new lessons (keeping sources fresh, giving the right access, customer records, alerts into restock decisions, reading reports, reviewing hours, reviewing receipts), common-mistakes sections, multi-question checks that must all be right in one go, **Try it with your own numbers** calculators, module-complete badges, and a read-only **Team training progress** view for account and HR managers. Written page guides now cover the Stock and Money tools that lacked one.


- **Appearance options, Herbal by default.** The account menu offers five appearances: Herbal (default), Light, Mist, Sepia and Dark. Herbal uses the company's own colors from herbalhealerscbd.com (deep teal-black text, teal accent, mint) on a soft green-tinted page with near-white cards, so the default is gentle rather than bright. Light keeps pure white cards for anyone who wants them, Mist is a dimmer blue-grey light, Sepia is warm paper with a muted blue-teal accent, and Dark is the teal-tinted dark (#111514 base, restored in #220). Each is a complete token set verified by `bin/check-palette-contrast`; the choice is remembered per browser. People who had never picked an appearance now see Herbal instead of Dark.
- **New color scheme, light and dark.** The warm Oatmeal palette (cream, taupe, olive, butter) is replaced by a blue-tinted neutral base with one blue accent, in both themes. The choice follows the color-preference literature: adults reliably prefer blues and dislike dark yellows, olives and browns (Palmer & Schloss 2010; Taylor et al. 2013), lower saturation and higher lightness read as calm rather than arousing (Valdez & Mehrabian 1994; Wilms & Oberfeld 2018), and pairs of similar hues with strong lightness contrast are judged most harmonious (Schloss & Palmer 2011). Dark mode uses dark grey surfaces rather than black with lighter, less saturated accents (Material dark-theme guidance). Every text/background pair meets WCAG AA 4.5:1 and every control border 3:1 in both themes; `web/bin/check-palette-contrast` reads the tokens out of the stylesheet and verifies this. Token names are unchanged, so views did not change; chart colors, shadows, the PWA manifest and the browser `theme-color` follow the new palette.

### Production readiness (2026-10-20)

- **Fix the Shopify GDPR webhooks.** `customers/data_request` and `customers/redact` crashed (route/controller/job names did not match) and all three compliance jobs were empty. They now verify, acknowledge fast, deduplicate on the delivery id, and redact mirrored customer data / record data requests for the operator. First tests for every webhook endpoint.
- **Refunds and cancellations reach Rupert.** Orders are fetched by `updated_at` on both platforms and Shopify/Square refunds become `Core::Refund` rows, so a refund issued days after the sale no longer overstates revenue.
- **Money is decimal.** Every amount conversion goes through `Money` on `BigDecimal`; typed refund/opening-cash amounts are validated.
- **Platform clients retry** rate limits (including Shopify `THROTTLED` with cost-based waits), 5xx and connection failures with bounded backoff; `SyncJob` retries transient failures and alerts once when it gives up.
- **Request throttling** (`rack-attack`) on login, signup, webhooks, the bearer API, public portals and the secret-bearing settings endpoints. **Optional Sentry** error tracking via `SENTRY_DSN`.
- **Encrypted Shopify offline tokens** (`ops:encrypt_shop_tokens` re-encrypts existing rows).
- **`GET /up/ready`**: database, worker heartbeat, sync freshness and disk in one readiness signal; the host watcher checks disk and the endpoint.
- **SQLite pragmas** (foreign keys, bounded WAL, cache) and a web-vs-job write-contention test.
- **Backups**: `bin/restore-drill` proves restore end to end with measured times; the off-host copy is encrypted, verified and shipped as a host timer; a backup/restore runbook states RPO/RTO.
- **Docker image builds and boots again** (build-time dummy secrets, explicit `HOST` requirement, bash on Alpine).
- **Shopify configuration**: API version pinned once (`config/shopify_api_version.rb`, checked against `shopify.app.toml`), `application_url` moved off a dead host, no built-in shop-domain default.
- **Repository hygiene**: `legacy/` (44 Dependabot alerts) and droplet-era units removed; `deploy/rupert-web-ser8.service` added; CI gains coverage floors on the sync engine and money paths, a whitespace check and a pinned artifact upload.
- **Docs**: operator runbook, backup/restore runbook, environment reference, release process, go-live checklist and the production readiness audit.
- Add Learn Rupert with personal getting-started paths, ten permission-aware lessons, worked examples, knowledge checks, saved progress and a searchable glossary. Days of the current week wait for the weekly sign-off instead of asking for daily approvals. The housekeeping audit loads lazily.

Expenses, vendor payments, bank-line decisions, day reviews, close packages and approvals dated inside a locked period then cannot be added, changed, moved or removed. Locks and reopenings are kept in a hash-chained ledger; reopening needs settings access and a written reason. Source imports that change a locked period are flagged on the lock page and in the books check.
