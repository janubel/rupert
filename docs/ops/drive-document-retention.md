# Automatic Google Drive document retention

Open **Money → Daily reconciliation & documents → Google Drive retention** (`/retention_drive`). A workspace administrator with `reports.write` and `settings.write` connects the Google account that should own the retention folder. Report readers can see progress and open verified copies; report writers can queue a retry. Connection and disconnection require both administrative settings and reporting permission.

Consent uses the platform’s existing OAuth client and registered `/auth/google/callback` with the limited `drive.file` scope. Retention has its own actor/workspace-bound state, ten-minute expiry and encrypted tenant-owned refresh token. It never reads or changes the whole-instance backup refresh token or folder. Google sign-in alone and the Drive connector available in a chat do not authorize unattended server uploads.

Once connected, the first copy pass is queued and `RetentionDriveJob` runs every fifteen minutes. Each pass handles up to 25 pending files, with a five-minute work budget and an atomic expiring lease to prevent overlapping passes. Further scheduled passes finish the backlog. **Sync now / retry** uses the same path. The destination is created privately with no sharing operations:

- `Rupert Document Retention — Workspace / Year / Month / Source / Originals`: retained reports, invoices, statements, screenshots and corrections.
- `Year / Month / Source / Native Exports`: all retained SwipeSimple transaction/invoice CSVs and Authorize.net portal CSVs, including historical exports.
- `Year / Month / Rupert / Report Archives`: immutable daily CSV and daily/weekly/monthly CSV/JSON versions.
- `Year / Month / Ctrax / Source Snapshots`: filtered normalized C-Trax JSON snapshots, explicitly distinguished from native originals.

Documents are filed by their covered period’s start date. Native portal exports are filed by the export’s received date, which does not establish transaction coverage. Filenames include a stable evidence reference, checksum prefix and original filename. Original bytes are uploaded without Google document conversion. A file that Rupert has not received cannot be copied: retain available invoices/statements through the daily page, or use the source’s supported original-export importer.

Remote file IDs are reserved and persisted before creation, so an interrupted response reuses the same ID rather than creating another copy. Every file is checked for the expected app identity, parent, trash state, size and MD5, then freshly downloaded to verify its SHA-256 against Rupert’s original. Only then does its receipt say **Copied** and expose a link. Failed uploads stay pending/failed for future retries; successful files are not rewritten or deleted. Verification is an upload-time guarantee, not a continuous audit of later edits or deletion in Drive. Shared folders and folder moves/trash detected during later uploads stop the affected uploads rather than silently changing the destination. Restore the original folder location and retry.

The encrypted local vault remains the primary retained evidence. Drive copies are ordinary source documents readable by the destination account, subject to its Drive permissions. Rupert does not share them, prune older versions or apply the database-backup retention policy to them. Owners should preserve the folder’s intended private access. Disconnecting removes the saved retention token and stops new uploads while keeping both local evidence and existing Drive copies. Reconnecting the same account resumes the same folder/receipts; choosing a different account creates an independent destination/history.

If Google returns `403 access_denied` because the app is in Testing, the OAuth client’s developer must approve the intended test user or complete production setup. External Testing tokens for Drive expire after seven days: see [Google’s refresh-token expiration documentation](https://developers.google.com/identity/protocols/oauth2#expiration). The previously observed platform backup consent block is documented in [Google backup verification](google-backup-verification.md). Do not report retention connected until consent succeeds and an actual uploaded/downloaded file verifies.

Apply migration `20261017033000_create_retention_drive_connections` and preserve runtime encryption keys. Consistent backups include connection settings and copy receipts alongside the original vault. Retry/copy tests cover lost upload responses, corrupt downloads, exact native bytes, tenant isolation, batching, paused connections, OAuth replay/expiry and permissions. No accounting or vendor records are mutated by the copy job.
