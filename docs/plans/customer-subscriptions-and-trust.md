# Customer subscriptions and customer-controlled access

Owner decisions, 2026-10-20: free Google account creation and system access; USD 499/month standard subscription; existing paying customers can refer a new customer for USD 249.50/month for the first 12 months with a 12-month commitment (USD 2,994 before tax), then USD 499/month. Bill through CSP Cyber Security Pilot's Stripe account. Customers must explicitly permit support access. Eventually infrastructure operators should not be able to decrypt protected customer data without customer sharing.

## Implemented in this branch

- Commercial landing pages for Rails `/` and GitHub Pages `/docs/index.html`; generated product documentation moves to `overview.html`. Anonymous landing access preserves signed-in account/workspace suspension checks.
- `/start`: verify Google email and subject before atomically creating a tenant, customer admin, exact-email Google identity, initial chart of accounts and free subscription record. Personal Gmail accounts work without allowing the entire Gmail domain. Repeat/conflicting registrations fail safely; public registration never grants platform privileges. Legacy reviewed company-domain admission remains available at `/signup`.
- `/billing`: owner-only monthly/referral checkout, explicit versioned commitment acceptance, active-paying-customer referral eligibility, no self-referrals, stable checkout idempotency key and reusable pending session. Prices and discounts are server selected. CSP account, USD 499 monthly price and 50%-for-12-months coupon are verified before checkout. No card data enters Rupert.
- Signed, timestamp-checked Stripe webhook endpoint. A browser redirect never marks a customer paid. Webhooks retrieve current Stripe state rather than trusting delivery order or event status fields. Subscription/customer/tenant/price bindings are checked. Free sign-in is independent of payment state; paid subscription state is recorded but no premium feature gates are introduced without a defined paid/free feature matrix.
- Customer-issued one-hour, named-operator read grants, revocation, expiry, encrypted support reasons, and an access audit. Browser support access permits an explicit controller list and blocks writes and credential settings. Cross-workspace bearer tokens can no longer bypass customer permission. Named operators enter support through the platform dashboard and can leave even after a grant expires. Browser full-instance backup exports/links are blocked when another customer subscription exists. Private platform overview remains operational metadata.
- Platform administration includes subscription states, commitments, referral attribution, operator identity readiness and support audit events alongside admission queues, account/workspace counts, sync/job/backup evidence. These are subscription-state summaries, not Stripe revenue accounting.
- Explicit owner identity-link task for the three supplied mailboxes. It only links to an existing active super administrator, refuses account conflicts and preserves identity-subject pins. It does not create privileges based on an email allowlist.

## What is not implemented or live

This branch has not been deployed. No Stripe products, keys, coupons, customer charges or production identity changes were created. Real CSP account ownership, live Google redirect configuration, DNS and production recovery remain to be checked.

New free workspaces currently use Rupert's existing shared, tenant-scoped database. This is NOT a separate SQLite database per customer. Customer-held encryption is NOT implemented. The support gate is an application boundary; server/DB operators, unscoped maintenance code and background integrations remain capable of accessing server-held data. Existing data exports/backups and connections must be reviewed before promising complete customer isolation.

## Phase 2 — a separate SQLite deployment per customer

Choose per-customer Incus/process isolation rather than switching Rails' global connection on each request. Keep a small control-plane database for identities, billing, provisioning states and non-sensitive health summaries. Each workspace gets a stable UUID, separate app process/container, encrypted volume and SQLite files, Rails encryption keys, provider secrets, queues and backup credentials. Never derive filesystem paths from a supplied subdomain/email. Use an authenticated internal provisioning API and queue, not customer-triggered shell commands.

Implement a durable, idempotent state machine (`requested → provisioning → ready` or `failed`), resource quotas, cleanup/retry rules and a signed, short-lived identity handoff to the target instance after successful Google verification. No tenant becomes usable until migrations, schema seed, key installation and health checks pass. Route allowlisted workspace hostnames to the correct instance through the reverse proxy; reject unknown/wrong-host sessions and do not share a broadly scoped session cookie.

Tenant data, job payloads, uploads and credentials must stay inside the customer instance. The platform dashboard reads only an authenticated summary API. Provider sync workers receive only their own tenant secrets. Restrict backup storage and recovery keys separately, perform restore drills, and test tenant-A identity against tenant-B DB/API/uploads/backups/jobs. Existing customers require a measured export/migrate/reconcile cutover, rollback point and provider scheduling pause. Merely creating an unused SQLite file is not isolation.

## Phase 3 — customer-held keys and secure support sharing

Threat model: protect against an application administrator and stolen database/backups; separately consider a malicious host operator who can alter delivered browser code or read server memory. Rails encryption protects database contents with app-held keys, not against someone who controls that app. Per-tenant KMS keys improve separation and revocation but do not by themselves meet operator-blind encryption when the server can request decryption.

Build a protected vault first for selected documents/records, using an audited authenticated-encryption library (for example AES-256-GCM with correct per-message nonces) and a maintained hybrid public-key scheme for wrapping data keys. A customer-generated private key remains in a customer-controlled device/agent; the server stores ciphertext, key IDs, nonces and recipient-wrapped keys. Use maintained HPKE implementations where appropriate; do not invent a PGP-like protocol or upload a customer's private key to Rupert. Bind ciphertext to tenant/record/version with authenticated associated data. Do not store plaintext copies in indexes, logs, notifications, exports or backups.

For support, the customer selects exact records, recipient and duration. The customer device re-encrypts a scoped data key to the verified support recipient public key. Require recipient-key verification, key versioning, a customer-visible sharing receipt and an audit. Never share the entire tenant master key or provider refresh tokens for a support session. Revocation stops future service access; it cannot erase plaintext or keys already copied by a recipient. Expiry alone cannot cryptographically revoke an already delivered decryption key; key rotation/re-encryption is needed for future ciphertext.

Google login and encryption-key recovery are separate. Offer an offline customer-owned recovery kit and deliberate device-to-device transfer. No operator reset path may silently decrypt old data. Losing every customer recovery secret means loss of protected data unless the customer explicitly chose escrow, which changes the security guarantee.

Always-on provider sync needs usable OAuth refresh tokens and sees provider plaintext while importing. Strict operator-blind operation therefore requires a customer-hosted connector/key agent (or a separately analyzed confidential-computing design), plus client-side reporting/search where necessary. A server-only Rails service cannot both freely decrypt records for background processing and promise its operator can never decrypt them. Before extending encrypted storage to operational ledgers, define how computation, search, multi-user access, payroll exports and key rotation work.

A malicious server delivering browser code could steal browser-held keys. Avoid an unconditional zero-knowledge claim for an ordinary web client; evaluate signed independently distributed clients/customer-run agents, reproducible builds, independent security review and the precise trusted components. Complete a reviewed key lifecycle and adversarial restore/share/revoke test suite before any stronger privacy claim.
