# Customer subscriptions and customer-controlled access

Owner decisions, 2026-10-20: free Google account creation and system access; USD 499/month standard subscription; existing paying customers can refer a new customer for USD 249.50/month for the first 12 months with a 12-month commitment (USD 2,994 before tax), then USD 499/month. Bill through CSP Cyber Security Pilot's Stripe account. Customers must explicitly permit support access. Eventually infrastructure operators should not be able to decrypt protected customer data without customer sharing.

## Implemented in this branch

- Commercial landing pages for Rails `/` and GitHub Pages `/docs/index.html`; generated product documentation moves to `overview.html`. Anonymous landing access preserves signed-in account/workspace suspension checks.
- `/start`: verify Google email and subject before atomically creating a tenant, customer admin, exact-email Google identity, free subscription record and isolated-instance provisioning request. The chart of accounts is seeded only inside the customer instance. Personal Gmail accounts work without allowing the entire Gmail domain. Repeat/conflicting registrations fail safely; public registration never grants platform privileges. Legacy reviewed company-domain admission remains available at `/signup`.
- `/billing`: owner-only monthly/referral checkout, explicit versioned commitment acceptance, active-paying-customer referral eligibility, no self-referrals, stable checkout idempotency key and reusable pending session. Prices and discounts are server selected. CSP account, USD 499 monthly price and 50%-for-12-months coupon are verified before checkout. No card data enters Rupert.
- Signed, timestamp-checked Stripe webhook endpoint. A browser redirect never marks a customer paid. Webhooks retrieve current Stripe state rather than trusting delivery order or event status fields. Subscription/customer/tenant/price bindings are checked. Free sign-in is independent of payment state; paid subscription state is recorded but no premium feature gates are introduced without a defined paid/free feature matrix.
- Customer-issued one-hour, named-operator read grants, revocation, expiry, encrypted support reasons, and an access audit. Browser support access permits an explicit controller list and blocks writes and credential settings. Cross-workspace bearer tokens can no longer bypass customer permission. Named operators enter support through the platform dashboard and can leave even after a grant expires. Browser full-instance backup exports/links are blocked when another customer subscription exists. Private platform overview remains operational metadata.
- Platform administration includes subscription states, commitments, referral attribution, operator identity readiness and support audit events alongside admission queues, account/workspace counts, sync/job/backup evidence. These are subscription-state summaries, not Stripe revenue accounting.
- Explicit owner identity-link task for the three supplied mailboxes. It only links to an existing active super administrator, refuses account conflicts and preserves identity-subject pins. It does not create privileges based on an email allowlist.

## What is not implemented or live

The commercial control plane has not been deployed. No Stripe products, keys, coupons, customer charges or production identity changes were created. Real CSP account ownership, live Google redirect configuration, DNS and production recovery remain to be checked.

New commercial registrations always queue a separate SER8 instance and cannot open business screens in the control-plane database. Host provisioning remains disabled until the clean image, restricted Incus project, routing import and trusted worker are installed and verified. Existing legacy workspaces and the older manually reviewed company-domain admission path retain their current tenant-scoped shared database until a separate migration. Customer-held encryption is NOT implemented. The support gate is an application boundary; server/DB operators, unscoped maintenance code and background integrations remain capable of accessing server-held data. Existing data exports/backups and connections must be reviewed before promising complete customer isolation.

## Phase 2 — a separate SQLite deployment per customer (SER8 selected by owner)

The implementation uses per-customer Incus/process isolation rather than switching Rails' global connection on each request. Keep a small control-plane database for identities, billing, provisioning states and non-sensitive health summaries. Each workspace gets a stable UUID, separate app process/container, encrypted volume and SQLite files, Rails encryption keys, provider secrets, queues and backup credentials. Never derive filesystem paths from a supplied subdomain/email. Use an authenticated internal provisioning API and queue, not customer-triggered shell commands.

The branch implements a durable, idempotent state machine (`requested → provisioning → ready` or `failed`), resource quotas, cleanup/retry rules and a signed, short-lived identity handoff to the target instance after successful Google verification. The host worker completes a lease only after migrations, schema seed, key installation, exact-revision local health and public HTTPS health checks pass. Expired leases fail closed and an operator can retry setup while preserving instance identity and keys. Sign-in handoffs are random, hashed, POST-only, single-use and valid for two minutes. Each instance exchanges its own handoffs with its own secret. A customer grant is revalidated centrally on each support read; denied writes and credential views do not run. Route allowlisted workspace hostnames to the correct instance through the reverse proxy; reject unknown/wrong-host sessions and do not share a broadly scoped session cookie.

Tenant data, job payloads, uploads and credentials stay inside the customer instance; the central database retains identity, billing, provisioning and support metadata. The platform dashboard reads only an authenticated summary API. Provider sync workers receive only their own tenant secrets. Restrict backup storage and recovery keys separately, perform restore drills, and test tenant-A identity against tenant-B DB/API/uploads/backups/jobs. Existing customers require a measured export/migrate/reconcile cutover, rollback point and provider scheduling pause. Merely creating an unused SQLite file is not isolation.

## Phase 3 — customer-held keys and secure support sharing

Threat model: protect against an application administrator and stolen database/backups; separately consider a malicious host operator who can alter delivered browser code or read server memory. Rails encryption protects database contents with app-held keys, not against someone who controls that app. Per-tenant KMS keys improve separation and revocation but do not by themselves meet operator-blind encryption when the server can request decryption.

Build a protected vault first for selected documents/records, using an audited authenticated-encryption library (for example AES-256-GCM with correct per-message nonces) and a maintained hybrid public-key scheme for wrapping data keys. A customer-generated private key remains in a customer-controlled device/agent; the server stores ciphertext, key IDs, nonces and recipient-wrapped keys. Use maintained HPKE implementations where appropriate; do not invent a PGP-like protocol or upload a customer's private key to Rupert. Bind ciphertext to tenant/record/version with authenticated associated data. Do not store plaintext copies in indexes, logs, notifications, exports or backups.

For support, the customer selects exact records, recipient and duration. The customer device re-encrypts a scoped data key to the verified support recipient public key. Require recipient-key verification, key versioning, a customer-visible sharing receipt and an audit. Never share the entire tenant master key or provider refresh tokens for a support session. Revocation stops future service access; it cannot erase plaintext or keys already copied by a recipient. Expiry alone cannot cryptographically revoke an already delivered decryption key; key rotation/re-encryption is needed for future ciphertext.

Google login and encryption-key recovery are separate. Offer an offline customer-owned recovery kit and deliberate device-to-device transfer. No operator reset path may silently decrypt old data. Losing every customer recovery secret means loss of protected data unless the customer explicitly chose escrow, which changes the security guarantee.

Always-on provider sync needs usable OAuth refresh tokens and sees provider plaintext while importing. Strict operator-blind operation therefore requires a customer-hosted connector/key agent (or a separately analyzed confidential-computing design), plus client-side reporting/search where necessary. A server-only Rails service cannot both freely decrypt records for background processing and promise its operator can never decrypt them. Before extending encrypted storage to operational ledgers, define how computation, search, multi-user access, payroll exports and key rotation work.

A malicious server delivering browser code could steal browser-held keys. Avoid an unconditional zero-knowledge claim for an ordinary web client; evaluate signed independently distributed clients/customer-run agents, reproducible builds, independent security review and the precise trusted components. Complete a reviewed key lifecycle and adversarial restore/share/revoke test suite before any stronger privacy claim.

### SER8 host implementation and activation

Host tooling is in `deploy/ser8/customer_provisioner.py`, `customer_bootstrap.py`, `customer_route.py`, `build_customer_image.py` and `setup_customer_project.py`. The worker has a private provisioning API token and Incus access on the host; Rails receives neither the Incus socket nor a privileged host shell. Jobs select only a reviewed immutable image from host configuration. Customer inputs never become shell commands. Worker commands pass sensitive bootstrap data over stdin, not process arguments, and HTTPS requests refuse redirects carrying credentials.

The dedicated project allows only unprivileged isolated-ID containers, no nesting, no host disk mounts, a dedicated managed NIC and loopback-only host proxies. The pilot budget is eight 1 GiB instances, one CPU each; change both project and worker limits deliberately. The dedicated IPv4 network blocks ingress between customers and private-service/metadata/management egress, permitting DNS/DHCP. Test this policy on SER8, including the correct provider/control-plane outbound routes, before admitting customers. Root storage in the existing `dir` pool does not provide a per-customer encrypted volume or a guaranteed disk quota; migrate to suitable storage or add an independently enforced storage budget before broad signup.

Build a clean application image from a clean OS image and the exact reviewed Git revision. The builder copies only the Ruby interpreter/public gems from the existing installation; it never copies production application data, settings or secrets. It removes SSH host keys, machine identity, logs and runtime files, and refuses an image containing a database or environment file. New instances generate independent Rails session and encryption keys. The template's embedded Shopify placeholders are not merchant credentials; customer integrations need their own explicit authorization. Stripe and Google login client secrets are not copied into customer instances.

Install the host scripts and service only after review. Prepare `/etc/caddy/rupert-customers` and a top-level `import /etc/caddy/rupert-customers/*.caddy` in the actual Caddy configuration, with a recorded rollback and successful validation. The route helper validates then reloads Caddy, and restores the previous route file on failure. It never changes wildcard DNS or existing route definitions. Configure the root-only worker environment with the reviewed image fingerprint/revision, canonical HTTPS control-plane origin and private worker token; configure the same token in the control plane. Enable `RUPERT_PROVISION_WORKSPACES=true` only when this path has passed staging acceptance.

Customer-held encryption remains Phase 3. Separate instances, independent app keys and support consent are not an operator-blind encryption guarantee. Backups currently contain the local database and environment keys; they require restricted storage and separately encrypted off-host recovery. Never present that backup arrangement as customer-held-key protection.
