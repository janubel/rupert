# C-Trax retail screens and daily register reconciliation

## Cashier and customer views

Open **Sell → C-Trax retail** (`/ctrax_pos`). The catalog is the selected store's native C-Trax variant snapshot, with source prices in USD, categories, signed/unknown stock and native IDs. Stock must have been read within 60 minutes to check a cart. Variable or missing prices require review in C-Trax. Prices, titles and images supplied by a browser are ignored when quoting.

**Pair customer screen** creates a private link for a second customer-facing browser/tablet. The link expires after 30 minutes and can be closed by its cashier. The customer sees the cart and chooses 10%, 15%, 20%, a custom amount or **No tip**; nothing is preselected. Suggested tips use the before-tax subtotal with half-up cent rounding. No intermediate choice is transmitted. Only confirmation stores a tip, and the cashier then sees the confirmed amount. A changed published cart or cleared cart invalidates that confirmation. Confirmations for an earlier cart revision are rejected. Deactivated cashiers, revoked POS permissions, inactive workspaces and expired/closed links cannot continue using the screen.

**Demo both screens** opens a web page with a cashier pane and customer pane, seeded from a real priced catalog item. This intentionally shows both perspectives for demonstration. In actual use, open the customer link on a separate display so the customer can make their choice privately. The customer view needs its own browser session for CSRF protection, but does not require a cashier login. Pairing tokens are random, filtered from request logs and encrypted in storage; treat a live link as access to that cart. Pages and status responses are not cached. Polling failures disable customer confirmation and clear unverifiable cashier totals.

## Real checkout

The paired screen now supports real **cash checkout**, receipts, register totals and a durable stock outbox. A settings/sales/inventory writer enables cash and paid-sale stock deductions in **POS checkout setup** for the selected store. Open a Rupert register for that location, pair the customer screen, build the cart and have the customer confirm an explicit tip choice. The cashier enters cash physically received; Rupert records the exact sale, tax, confirmed tip, tender and change atomically. Repeated submissions return the existing receipt. Closing a register is blocked while a checkout is unfinished. Cancel an unpaid checkout to release its local stock allocation and start a new cart revision.

Checkout refreshes the approved C-Trax stock feed before allocating managed native variants. Prices and assigned per-item store tax rates are checked again; a change invalidates tip confirmation and requires another review. Native tax relationships apply independently of the master-product price override flag. Explicit empty tax assignments mean zero; missing tax information remains unknown and blocks checkout. Tax is rounded per rate and per unit before multiplying quantity. Discounts, variable prices, split tenders, refunds/restocking, terminal payments and cash drops are not implemented by this checkout. Native discounted historical lines can use different tax rounding, so this does not claim parity with discounted C-Trax orders.

Paid sales are canonical Rupert orders with source `rupert_pos`. Revenue excludes tips; the payment and register tender total include the confirmed tip. These receipts are separate from C-Trax's native order journal and daily source reports; no guessed native order-creation endpoint is called. A local hold protects against overlapping Rupert cashiers; it cannot reserve stock against independent C-Trax sales. Do not simultaneously sell the same scarce stock through both interfaces without checking availability.

When paid-sale deductions are enabled, a worker submits native `inventoryAdjustments` using action `remove`, reason `other`, positive whole quantity and an exact Rupert sale/variant marker. The response must identify the store/variant and expected remaining quantity. A lost or unverifiable response stays pending/unknown and is never blindly resubmitted. Recovery uses an exact durable source marker; an incompatible source history needs operator/vendor review. The visible receipt lists each stock update status. This write contract was observed in the native vendor client and covered with transport/recovery fixtures; no production sale or stock mutation was executed for rollout testing.

## Private card checkout

**NMI sandbox integration, October 16:** the paired customer screen also supports a separate NMI sandbox gateway, hosted card tokenization and REST sale/query recovery. Production NMI charges are blocked in code. Sandbox receipts do not create live sales, register revenue or stock effects. Dedicated vendor-connected sandbox acceptance is pending credentials; see [setup, safeguards and test scope](ops/nmi-sandbox-checkout.md).

An optional Authorize.net **AcceptUI hosted form** collects card details on the customer display after tip confirmation and cashier checkout preparation. Rupert receives only an opaque one-use payment token; the server chooses the amount from the frozen checkout, never from browser fields. Setup requires the store's existing Gateway ID, API Login ID and Transaction Key, account identity/USD/public-client-key verification, then explicit enabling. Credentials are encrypted and never redisplayed. Reporting OAuth is separate from payment credentials. Sandbox and production are explicit; a production gateway in test mode is rejected. This implementation does not operate a PAX/TRX terminal.

A payment attempt and unique invoice are committed before sending a charge. Only matching gateway transaction details with approved capture state, invoice and exact full amount create a paid receipt. A decline permits a new token. Timeouts, held-for-review and mismatches remain unresolved; the customer and cashier must not repeat the charge. Background/manual reconciliation performs reads only, including unsettled and settled invoice lookup when a response was lost. The duplicate-window gateway option supplements the local state; `refId` is not treated as an idempotency key. Account/credential changes are blocked while card outcomes are unresolved. A gateway void/refund requires its existing operational process; Rupert cannot perform it here.

The code and gateway fixtures are implemented, but card activation and a real payment depend on verified merchant credentials and operator acceptance. No live card charge is claimed by this release. First-party contracts: [Authorize.net hosted AcceptUI](https://developer.authorize.net/api/reference/features/acceptjs.html), [transaction API](https://developer.authorize.net/api/reference/index.html), [duplicate-window behavior](https://support.authorize.net/knowledgebase/article/000001473/en-us).

**Demo both screens** traverses confirmation, cash/change or simulated customer card payment and receipt, explicitly labeled as a demonstration. It creates no canonical order/payment or source stock writes. Demo catalog age does not authorize a real checkout.

## Product images

C-Trax retail is the single POS screen; the retired Shopify preview redirects there. Only listed variants with a usable website image appear in the product catalog, categories and search. Filtering happens before pagination. Adding or linking a website image makes the product visible on the next catalog load. Inventory writers can link a hidden variant to a website image in the catalog’s setup disclosure. Source stock remains the C-Trax snapshot.

Images come from Rupert's existing read-only Shopify mirror of the main website (Herbal Healers uses herbalhealerscbd.com). Image association order is an explicit local mapping, native website product ID, unique exact SKU, then unique normalized parent title. Ambiguous and near-name matches are left unlinked. **Website image link** lets an inventory writer choose a mirrored website product. This changes only Rupert's image association; it never changes a source SKU, price or stock. Only HTTPS images from the Shopify CDN or the selected business website are displayed. There is no storefront crawl on each POS request.

## Daily source import

Open **Sell → C-Trax daily close** (`/ctrax_days`). A sales/sync writer can queue a selected business date. In **Settings → POS & payment connections → C-Trax**, a settings/sales writer may opt into scheduled sales reads. The production scheduler runs at minutes 5 and 35; each worker refreshes today and yesterday using the current Herbal Healers Eastern business calendar. Older corrections require a manual date read. This window is intentionally separate from stock reads at minutes 0 and 30. Both production workers and recurring scheduling must be active. Do not configure production integrations on localhost.

The saved encrypted C-Trax user authenticates afresh. Store metadata supplies `timezone_identifier`. The client sends `X-Store-Timezone` and `X-Client-Timezone`; orders use `completed_between` with store-local midnight timestamps and `override_timezone=store`. Local half-open day filtering includes a completion at the start and excludes the next midnight, including DST-length days. Orders, register sessions and cash drops are completely paginated with duplicate/native-ID and stable-total checks. Earlier opened sessions are fetched too, so an open or midnight-crossing register is not silently omitted. Existing request/time/size bounds apply and can reject very large histories instead of truncating them.

Each store/day snapshot keeps allowed order, payment and per-unit native line fields, source origin/store/timezone, report controls, read time and digest. Monetary fields remain signed integer minor units; absent amounts remain unknown. C-Trax emits one native line per unit; no invented quantity is assigned. Customer details, cardholder/account data, auth codes, terminal credentials and raw vendor payloads are excluded. Normalized daily financial snapshots are encrypted with the runtime Rails keys.

The independent `sales.general.summary` report uses **raw_json**. Detail count, total, tax, discount, tips and base tender totals are compared to report controls. Payment total is checked against base amount plus actual tip plus surcharge. Refunds, unknown tender/state/money and mismatches require review. A source refund count is retained, but detailed refund/restock execution is not implemented. Missing/empty controls never imply zero.

Register cash variance is shown only for a closed session wholly contained in the day, matched detail/report controls, known opening/count/drop amounts and no cash refunds or cash tips/surcharges whose drawer treatment is not verified. Open/cross-day sessions and incomplete movements stay **Unknown**. Cash drops are an observed endpoint; the live verification had no drops, so nonempty source amount compatibility still requires real evidence. This page is a source reconciliation, not bank settlement, processor fees or a declaration that a drawer is physically balanced.

A local review records the source digest and reviewer. An unchanged re-read preserves review; changed source facts require another review. Unresolved differences require a note. CSV exports include explicit count/minor-unit labels. Source registers are never closed or modified by Rupert. All store/day and image records are workspace scoped; only the creating cashier can manage a paired display.

## Items sold

Each store's daily close, and **View items sold** on the date page for all stores (`/ctrax_days/items?date=`), summarize completed, non-deleted receipt lines by C-Trax product/variant: units (one native line per unit), receipts, gross line amount, line tax, discounts, refunded units and net, with a CSV in minor units. Stored days have no line discounts, refund lines or SKUs. Order discounts are never allocated to items, so an item's discount/net stays **Unknown** when any of its receipts was discounted; refunded units stay Unknown when a receipt had a refund. SKU, barcode and category come from the current C-Trax stock read by native variant ID and stay Unknown when the variant is absent.

The tie-out compares item line amounts with order subtotals, line tax with order tax, and items − order discounts + tax + shipping + shipping tax with order totals. Any difference is shown. Tips, card surcharges and source report refunds are listed separately because they are outside order totals.

**Not in Rupert's catalog** lists sold variants without exact evidence (website IDs, SKU, barcode) for a current Shopify catalog item, using the Stock comparison matcher. An exact normalized name + explicit package match is only a review candidate. Nothing is created in Rupert, Shopify, Square or C-Trax.

## Operations and recovery

Publish a new version only after migration, loader/assets, regression and real read checks. Back up the production database consistently with its encryption/runtime keys before migration. Never put live reports, account credentials or those keys in the public source repository. Keep an encrypted off-machine runtime backup in the owner's verified private repository. A source bundle restores code, not authentication. See [stock identity and API limits](ctrax.md).
