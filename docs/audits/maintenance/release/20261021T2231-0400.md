### P0 — Host-loss protection is not yet proven current

Current source defines consistent SQLite snapshots using `VACUUM INTO`,
integrity checks, encrypted environment/settings sidecars, a host copy, an
off-machine mirror, and a weekly isolated restore check. The mirror and
Google Drive status are operational facts, not guaranteed by their source
files. The current [backup guide](../../../ops/backups.md) says the Drive
OAuth flow has not been accepted; the off-machine mirror requires a second
machine, and decrypting a recovery set requires the separately escrowed key.
The latest live gate comment explicitly says the
off-host copy and isolated restore remain unverified. Do not claim that
SER8-loss recovery or the current recovery point is accepted until that gate
has fresh evidence.

The source stores important business records in SQLite and encrypted values
require the matching Rails encryption keys. The retained PostgreSQL cutover
copy is frozen history and cannot be used as a rollback database. Code rollback
must preserve later SQLite writes and additive schema; database rollback
requires a separately approved reconciliation plan.

### P1 — Deployment gates do not prove queue quiescence or full readiness

The host auto-deployer requires a clean fast-forward, green `CI (sqlite3)`,
and takes a pre-deploy SQLite backup. It runs migrations and assets, restarts
web/jobs, checks `/up` and active units, and rolls code back on failure. It does
not revert migrations, and it does not gate on zero claimed/active jobs. The
Rails `/up/ready` check covers database reachability, a recent Solid Queue
worker heartbeat, sync freshness, and free disk; it does not prove that no job
is claimed. Current service units have a 60-second stop timeout; the web unit
supports Puma `SIGUSR2` reload. Prior receipts document an Incus/AppArmor
signal problem and the Oct 21 live gate documents a later auto-deploy. The
current host behavior and restart procedure need verification before another
promotion; no old restart command was run.

Migrations must remain additive and backward-compatible. October 17 rehearsed
the two then-pending migrations down/up and verified idempotence. This audit
did not inspect the live schema or establish migration compatibility for all
source changes after that receipt.

### P1 — Published deployment guidance understated merge side effects

`docs/deployment.html` said no automated production deploy was configured,
while the current SER8 host updater polls `main` and can deploy a green,
fast-forward commit after taking a pre-deploy SQLite backup. A tag-created
GitHub Release does not itself deploy; merging to `main` can cause the host
updater to act. The docs now describe that distinction and link to the updater
gates. The installed mode and latest deployed SHA still require live evidence.

## Acceptance and recovery checklist

1. Record the intended full release SHA and all applicable checks for that
   exact SHA; inspect production under the existing lock and preserve newer
   deployed work.
2. Verify installed host and mirror scripts against reviewed repository
   versions. Confirm fresh snapshot, encrypted off-host set, separate key
   escrow, and mirror freshness.
3. Restore that set into a new isolated nonproduction destination. Check
   checksums, SQLite integrity and foreign keys, expected business counts,
   retained files, and decryption of encrypted settings with the matching
   keys. Record measured RPO/RTO.
4. Rehearse migration compatibility and code rollback while preserving new
   SQLite writes. Before activation, verify the host-specific graceful
   shutdown/restart procedure, zero claimed jobs, worker heartbeat, sync
   freshness, health and disk headroom.
5. After promotion, record the exact running SHA, applied migration versions,
   `/up` and `/up/ready`, web/jobs state, backup freshness, and authenticated
   Projects/Tasks acceptance. Keep payment, inventory-source and operator
   acceptance separate from source/fixture success.
